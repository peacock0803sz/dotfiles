# archviz

ソフトウェアの構造や振る舞いを伝える技術図を、ベクター形式で作る。最終成果物は `.svg`、または `.drawio` とその SVG 書き出しの組。

良い技術図は、読み手が抱いている一つの問いに答える。「全部載せた図」は誰の問いにも答えない。このスキルの手順は、描く前に問いと要素を固め、描いた後に実際にレンダリングして確かめる、という二点を外さないためにある。

## 手順

### 1. 図の問いを決める

依頼から次の三点を読み取る。読み取れなければ短く質問する。

- 読み手: 新メンバー、レビュアー、運用担当、経営層など。読み手で抽象度が決まる
- 問い: 「どこに何が動いているか」「リクエストがどう流れるか」「どこが信頼境界か」など、この1枚で答えること
- 図の種類: 下の表から選ぶ。問いが複数あるなら図を分ける

| 問い | 図の種類 |
|---|---|
| システムは誰と何に囲まれているか | C4 コンテキスト図 |
| 実行単位(プロセス、サービス、DB、キュー)とその通信 | C4 コンテナ図 / コンポーネント図 |
| 1つの処理が時間順にどう進むか | シーケンス図 |
| データがどこで生まれ、変換され、どこに溜まるか | データフロー図 |
| 何がどのマシン、ネットワーク、リージョン、デバイスに載るか | デプロイ/ネットワーク図 |

1枚に載せる要素は 20 前後までにする。それを超えるなら、抽象度を一段上げるか、サブシステムごとに図を分ける。

### 2. 素材を集める

- コードベースから描く場合は [references/from-codebase.md](references/from-codebase.md) を読む。図の種類ごとに見るべきファイルをまとめてある。推測で要素を足さず、根拠ファイルを押さえる
- 説明から描く場合、図の骨格に効く不明点(通信が同期か非同期か、どこが外部システムか等)は質問する。些細な不明点は仮置きし、納品時に「仮定」として報告する

### 3. モデルを書き出す

描き始める前に、ノード、グループ(境界)、エッジを表か箇条書きで書き出す。

- ノード: 名前、種別(サービス/DB/キュー/外部…)、技術(例: Go, PostgreSQL)
- グループ: 信頼境界、デプロイ単位、チームなど、何でくくるのかを一つに決める。基準を混ぜると境界の意味が読めなくなる
- エッジ: 向き、ラベル(何を/どのプロトコルで)、同期か非同期か

要素が10を超える図やコードから起こした図は、このモデルをユーザーに見せて合意してから描く。レイアウトを直すより、モデルの段階で直す方がずっと安い。

### 4. エンジンを選ぶ

| 状況 | エンジン | 詳細 |
|---|---|---|
| 既定。境界の入れ子がある構成図、デプロイ図、シーケンス図 | D2 | [references/d2.md](references/d2.md) |
| GUI で手直ししたい、Confluence 等の draw.io 連携に載せたい、ユーザーが drawio を指定 | `scripts/spec2drawio.py` → .drawio | [references/drawio.md](references/drawio.md) |
| 要素が少ない概念図、レイヤ図、スタック図など、自動レイアウトだと意図した配置にならないもの | SVG 手書き | [references/svg.md](references/svg.md) |
| 数十ノード以上の依存グラフ(import グラフ、パッケージ依存など) | Graphviz | [references/d2.md](references/d2.md) 末尾 |

Mermaid は、Markdown にコードブロックとして埋め込むとユーザーが指定したときだけ使う。mmdc は Chromium が必要で、ベクター画像を作る目的だと割に合わない。

ツールは未インストール前提で、`nix run nixpkgs#<pkg>` を使う(nix-run スキルの流儀)。

### 5. 描く

表記の規律は [references/design.md](references/design.md) に従う。特に大事な点は次のとおり。

- 形は種別、色は所属や境界、線種は通信方式を表す。一つの図の中で意味を変えない
- エッジには動詞かプロトコルのラベルを付ける(`HTTPS/JSON`, `publish OrderPlaced`)
- 番号は丸数字(①)ではなく `1.` や `(1)` で振る
- タイトルを付け、記号の意味が自明でなければ凡例を付ける
- 主な流れを左→右(または上→下)に揃える

### 6. レンダリングして確認する

生成したら必ず PNG にして自分の目で見る。SVG のソースを読むだけでは、文字のはみ出しや線の突き抜けに気づけないからだ。

```bash
rsvg-convert -w 1600 out.svg -o <scratchpad>/check.png   # D2 / 手書きSVG / Graphviz
nix run nixpkgs#drawio -- -x -f png --scale 1.5 -o <scratchpad>/check.png out.drawio   # drawio
```

PNG を Read で開き、次を確認する。問題があれば直して再レンダリングする。

- [ ] ラベルが図形からはみ出していない、文字同士が重なっていない
- [ ] エッジが無関係なノードの上を突き抜けていない
- [ ] 手順3のモデルの要素とエッジがすべて載っている(数を突き合わせる)
- [ ] 矢印の向きが呼び出し/データの向きと一致している
- [ ] タイトルと、必要なら凡例がある
- [ ] 日本語が豆腐(□)になっていない

rsvg は D2 のエッジラベルの背景マスクを描かないので、線がラベルの文字を貫いて見えることがある。ブラウザでは正しく表示されるので、これは問題として扱わない。

2〜3回直しても自動レイアウトが意図どおりにならないなら、エンジンを変える(D2 のレイアウトを elk↔dagre で切り替える、手書き SVG に切り替える)。

### 7. 納品する

- ソース(`.d2` / `.drawio` / 手書きなら `.svg` 自体)と `.svg` を同じ場所に、同じベース名で置く。ソースが残っていれば後から直せる
- 出力先の指定がなければ、リポジトリ内なら `docs/diagrams/` を提案する
- 報告には、成果物のパス、図が答える問い、置いた仮定、コードから起こした場合の主な根拠ファイルを含める
